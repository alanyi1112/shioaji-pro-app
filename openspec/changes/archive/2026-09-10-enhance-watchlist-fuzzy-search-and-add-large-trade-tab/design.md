## Context

自選清單目前以 `src/lib/stock-index.ts` 與 `src/lib/product-search.ts` 產生候選。股票代號覆蓋範圍大於名稱資料，名稱缺漏時候選會退化成只顯示代號；現行排序也以代號前綴與名稱包含為主，未處理全半形、空白／符號、近似字串、非同步競態及完整鍵盤選取。專案內的 MultiView 已有 `/api/instrument-search` 與台灣商品目錄評分邏輯，可在不直接複製另一份大型目錄的前提下共用。

成交明細目前由 `src/components/tick-tape.tsx` 合併歷史 ticks 與 SSE ticks，只保留最近 120 筆。既有大單判斷是「至少 5 張且大於目前樣本平均量 3 倍」，樣本少於 10 筆時不啟用，且候選成交會參與自己的平均值；這個規則沒有獨立頁籤、金額門檻或固定的偵測結果，也可能因歷史與即時資料重疊而重複計算。

台灣看盤軟體對大單沒有唯一市場標準。公開資料常見兩類做法：依股價換算單筆金額／張數的固定分級，以及依近期成交金額分布建立動態門檻。本設計採兩者取嚴格值，讓高價股不會因固定金額過低而過度觸發，也讓活躍股能隨近期成交分布調整。

參考資料：

- [XQ：大單與特大單](https://www.xq.com.tw/learn/beginner/blocktrades/)：以單筆成交金額分級，並排除開收盤等非連續撮合。
- [CMoney：盤中即時大戶散戶](https://www.cmoney.tw/notes/note-detail.aspx?nid=742578)：以成交金額搭配個股過去平均金額動態設定門檻，並以 400 元股票至少 5 張、約 200 萬元為例。
- [XQ：台股逐筆撮合的連續成交 Tick 序列](https://www.xq.com.tw/learn/xspractice/tickseq/)：說明非逐筆撮合標記，以及同一委託產生多筆連續成交時應合併觀察的限制。

上述公開產品沒有共同且可直接移植的單一標準，也沒有公開本 change 採用的確切 P70 參數。本 change 的「40 萬元、5 張價值、前置樣本 P70 三者取高」是依公開產品共同採用的成交金額、股價差異與動態門檻概念所做的可重現產品決策；P70、30 筆暖機與 120 筆視窗均由本規格明確定義，不宣稱為任一外部產品的原始算法。

## Goals / Non-Goals

**Goals:**

- 讓使用者能以台股代號或股名的近似文字找到正確商品，並在加入前完成明確選取與 contract 驗證。
- 在 MultiView 搜尋來源不可用時保留既有搜尋與精確代號加入能力，不讓外部面板成為自選清單的單點故障。
- 提供可解釋、可重現、以金額為基礎的大單分類，並在成交明細面板直接顯示當下使用的門檻。
- 保持 history/live 合併、一般面板與 popout、商品切換及交易日切換的一致性。
- 不增加行情 subscription、不啟用 production、不下單，也不改變 broker 或交易狀態。

**Non-Goals:**

- 不建立跨裝置、跨重新整理或完整交易日的大單永久資料庫；第一版只維護目前面板生命週期內的有界資料。
- 不將「大單」解讀為特定投資人、大戶、主力或買賣方向身分。
- 不以現有欄位猜測處置股票的逐筆撮合模式；若未來行情來源提供權威撮合模式，才另行擴充排除規則。
- 不重做 MultiView 商品目錄、不取代 Shioaji contract 驗證，也不改變非台股商品既有搜尋流程。

## Decisions

### 1. 抽出可共用的台灣商品搜尋 client，現有盤中監控 wrapper 保持相容

將 `src/lib/intraday-monitor-instrument-search.ts` 內與面板無關的請求、timeout、schema 驗證與錯誤型別抽成共用模組；原匯入路徑保留 wrapper，避免影響進行中的盤中監控 change。自選清單只對台灣 `STK` 查詢 MultiView `/api/instrument-search`，並與 `searchProducts` 結果合併。

候選鍵固定為 `securityType + exchange + code`。同鍵候選以具有正式名稱、來源更新時間及欄位完整度較高者優先，避免同一商品重複出現。

替代方案是把 MultiView 完整目錄複製到 5173 bundle；這會產生兩份目錄與更新節奏，故不採用。另一替代方案是只依賴 5174；這會讓 MultiView 停止時無法加入自選股，也不採用。

### 2. 搜尋正規化與排序採可測試的決定性規則

查詢與候選欄位先做 Unicode NFKC、trim、大小寫折疊，並移除空白及常見分隔符號。排序依序考量：代號完全相等、代號前綴、名稱完全相等、名稱前綴、名稱包含、名稱 bigram Dice／edit similarity 取高的相似度；同分時以交易所、代號及名稱穩定排序。模糊候選必須通過最低相似度，不以低信心結果自動加入。

UI 使用短 debounce 並為每次查詢配置 request id／AbortController；過期回應不得覆寫新查詢結果。方向鍵移動目前候選，Enter 只加入已明確選取或唯一精確候選，Escape 關閉候選。輸入純代號時保留既有直接 contract 查詢能力。

### 3. 候選顯示與最終驗證分離

MultiView 與本機索引只提供候選的 `code`、`name`、`exchange`、`securityType`。按下加入後，仍以既有 Shioaji contract API 解析 canonical contract；驗證失敗不得建立 watchlist item。這可避免目錄過期或模糊比對錯誤成為正式自選清單資料。

載入中、搜尋來源離線、搜尋錯誤、沒有結果與 contract 驗證失敗必須是不同狀態；來源離線時仍顯示本機候選，不能將「只剩降級結果」誤報為「沒有商品」。

### 4. 大單以「固定保底、5 張價值、近期 P70」三者取高

每筆合格成交以相同公式計算：

```text
tradeAmount = price × volume(common_lot) × 1,000
fixedFloor = max(400,000 TWD, price × 5 × 1,000)
dynamicFloor = 前 120 筆合格成交金額的 P70
threshold = max(fixedFloor, dynamicFloor)
large = tradeAmount >= threshold
```

P70 採 nearest-rank：將前置樣本由小到大排序，取 `ceil(0.70 × n) - 1` 的零基索引。動態門檻至少需要 30 筆前置合格成交；不足時只採 `fixedFloor`，並顯示「動態門檻暖機中 n/30」。目前候選成交必須先分類、再加入前置樣本，避免影響自己的門檻。

例如股價 15 元時固定門檻為 40 萬元，約需 27 張；股價 200 元時為 100 萬元／5 張；股價 400 元時為 200 萬元／5 張。此規則比單純張數更能比較不同價位，也比單純近期平均值更不容易被極端值拉動。

替代方案包括沿用 5 張加平均量 3 倍，或採單一固定金額。前者無法跨股價比較且會回溯漂移，後者會對高價股過度敏感，因此不採用。

### 5. 大單資格以可驗證的 regular-lot 即時欄位為限

第一版只分類台灣上市／上櫃 `STK` 的 regular-lot 真實成交。`volume <= 0`、`intraday_odd=true`、`simtrade=true`、價格或時間無效者均排除。時間必須晚於 `09:00:00` 且早於 `13:25:00`（Asia/Taipei），排除可辨識的開盤與收盤集合競價成交。

現有 tick payload 沒有可靠的處置／分盤撮合模式欄位，因此第一版不從商品名稱或成交節奏猜測；這項限制保留在設計與測試，不在介面顯示使用者已要求移除的身分免責句。

### 6. 分類事件不可變，並以穩定鍵去重

每個已分類大單保存 `tradeKey`、商品、交易日、成交時間、價格、張數、成交金額、`thresholdAtDetection`、`ruleVersion` 與來源。`tradeKey` 由 canonical 商品鍵、交易日、標準化時間、價格、張數及 `tick_type` 組成；history 與 live 出現相同鍵時只保留一筆，live 可補足來源資訊但不得重複影響動態樣本。

門檻只用事件之前的資料計算。已分類結果不因後續樣本改變而重算，以確保使用者看到的筆數不會倒退。商品、交易日或 stream generation 改變時，分類器與 UI 資料必須隔離／重設，不得跨商品或跨日污染。

### 7. UI 採成交明細內部頁籤，並維持有界記憶體

成交明細表頭新增「全部」與「大單 N」。兩個頁籤沿用同一列 renderer、欄位與方向色彩；大單頁籤另顯示兩行精簡條件：目前金額門檻，以及「門檻＝40 萬元、5 張價值、近 120 筆 P70 三者取高」。不顯示「大單成交篩選，並非交易者身分判定」。

「全部」保留現行 120 筆上限；「大單」在目前商品、交易日與面板生命週期內最多保留 500 筆。一般面板與 popout 共用相同分類工具與資料模型，避免同一串流在不同 UI 產生不同判斷。

## Risks / Trade-offs

- [MultiView 搜尋服務暫時不可用] → 使用硬 timeout、取消過期請求及本機搜尋降級，保留精確代號 contract 驗證。
- [不同來源的名稱或交易所標記不一致] → 以 canonical 候選鍵合併，最終由 Shioaji contract 決定正式商品資料。
- [短期成交分布劇烈改變造成門檻跳動] → 使用前置樣本 P70、30 筆暖機及固定保底；每筆事件保存偵測門檻，不回溯改寫。
- [歷史與即時時間精度不同造成去重失敗] → 在 adapter 層統一交易日、時間、價格及 common-lot 單位，再建立穩定鍵；為重疊分鐘加入測試 fixture。
- [現有 Shioaji tick payload 沒有 `SeqNo`／`TickGroup`] → 第一版以商品、日期、微秒時間、價格、張數及 `tick_type` 建立穩定鍵，且逐列分類；無法還原同一委託產生的連續成交群組，也可能把欄位完全相同的成交視為重播。介面不宣稱支援委託群組級大單，待來源提供權威欄位後另立 change。
- [只保留頁面生命週期資料，無法代表全天] → UI 只呈現本次載入與啟用後可取得的成交，不宣稱永久保存或完整交易日統計；完整持久化另立 change。
- [處置股票撮合模式無權威欄位] → 不以推測排除或標註，將權威 matching mode 留作後續資料契約擴充。

## Migration Plan

1. 先建立純函式的搜尋正規化／合併／排序與大單分類／去重模型及 fixtures。
2. 抽出共用商品搜尋 client，保留既有盤中監控匯入介面並完成回歸測試。
3. 將自選清單接上非同步候選與鍵盤選取，維持既有 direct-code 與非台股商品流程。
4. 將 TickTape 改為標準化事件管線，加入頁籤、條件顯示及有界大單紀錄。
5. 以 unit、component、browser、build 與 OpenSpec strict validation 驗證；只在 simulation 環境做 UI 檢查。
6. 若回歸異常，可獨立回退自選清單搜尋 UI 或大單頁籤；既有商品加入與全部成交明細仍保留。

## Context

MultiView 的線圖卡片已可在同一頁籤內拖曳排序，`renderMarketTabs` 會建立頁籤標題，卡片亦已有右鍵功能表。現有 `user_instruments` 以 `(user_id, symbol, tab_id)` 為主鍵；個人頁籤使用自身 ID，但系統頁籤的覆寫都使用空的 `tab_id`。因此只串接目前的新增、刪除與排序 API，無法讓同一商品同時可靠地存在於兩個系統頁籤，也不能保證跨頁籤「移動」不留下半成品。

線圖卡片另有 `canonicalItem`（所屬清單項目）與 `symbolSelect.value`（暫時顯示的商品）兩種狀態。拖放與快捷移除只可作用於已驗證的清單成員，不可把使用者暫時觀看的其他商品誤當成待刪清單項目。變更須維持既有 MultiView／RealTimeStock 清單隔離及 simulation-only 交易邊界，並避開工作區中其他進行中的變更。

## Goals / Non-Goals

**Goals:**

- 從線圖商品卡片拖到啟用頁籤標題，預設移動、放開時 Option 複製；目的商品置頂，來源與目的地狀態可預期。
- 以右鍵功能表及卡片標題 `⋯` 操作入口執行移動、複製、快捷移除；確認移除的目標與結果清楚。
- 使系統及個人頁籤的商品成員資格能以穩定頁籤 identity 分別持久化，並使跨頁籤 mutation 具原子性、衝突檢查與回讀確認。
- 維持既有頁籤內拖曳排序、目前作用中頁籤、未受影響線圖、K 線與行情連線。

**Non-Goals:**

- 不合併或改寫 RealTimeStock／Shioaji 自選清單，不變更交易權限、下單或行情訂閱策略。
- 不從清單永久刪除商品 catalog、歷史 K 線或籌碼資料；不提供一次拖曳多檔商品。
- 不以滑鼠懸停頁籤自動切換頁籤；不將臨時從代號選單切換的顯示商品自動加入或移除清單。

## Decisions

### 1. 沿用卡片拖曳，僅以商品標題手把啟動跨頁籤操作

沿用 `state.panelDrag` 的 pointer lifecycle、取消條件及預覽清理，新增「頁籤標題落點」判斷。指標捕捉後依座標尋找目的頁籤，不能只看被 capture 的 `event.target`。手把在單圖與多圖都可啟動跨頁籤操作；原本線圖區域的頁籤內排序仍維持原樣，但不能從線圖繪圖／拖曳區直接觸發跨頁籤寫入，以免與縮放、移動視窗或繪圖手勢衝突。目的頁籤 hover 只提供名稱、移動／複製及合法性預覽，不切換頁籤。模式以 drop 當下的 `altKey`（Mac Option）決定；Escape、pointercancel、blur、visibilitychange、滑鼠按鍵提前放開或無效落點均取消並清除視覺狀態。

考慮過直接用瀏覽器原生 HTML Drag and Drop，但既有卡片採 pointer capture、同頁籤排序及畫布互動；兩套拖曳生命週期並存容易造成幽靈拖曳、事件競爭與圖表操作衝突，因此採用單一現有控制器延伸。

### 2. 快捷操作只綁定確定的清單成員，並以雙入口提升可發現性

可操作目標取自 `activeMarketTab()` 的穩定 `tabIdentity` 與卡片 `canonicalItem`。只有卡片顯示代號與 canonical 代號一致、且伺服器仍能確認來源成員時，才允許轉移或移除；不一致時選單以停用項與原因提示呈現，不對任一代號做猜測。右鍵功能表與標題 `⋯` 共用同一套「移動到…／複製到…／從『頁籤』移除『商品』…」操作；目標選單只列出其他啟用頁籤。移除以可取消、支援鍵盤的確認對話框展示頁籤及代號，確認前不寫入。

考慮過只在右鍵選單放「刪除」，但它不可發現，也無法區分移除清單成員與刪除圖表／商品資料；改用帶頁籤名稱的「移除」與可見入口。

### 3. 系統頁籤改為按頁籤 identity 持久化覆寫

為系統頁籤新增按 `(user_id, system_tab_id, symbol)` 唯一的成員覆寫儲存，記錄存在／隱藏、排序及必要的個別商品 metadata。共享預設清單保持唯讀；有效清單由預設資料、既有個人覆寫及新 per-system-tab 覆寫合併，並由新覆寫優先。個人頁籤維持既有以 `tab_id` 區分的資料。讀取與既有新增、移除、排序、還原頁籤 API 均須共用有效成員解析，不能只讓新快捷 API 看得到新增的系統頁籤商品。

既有 `tab_id=''` 系統覆寫需以已知的穩定系統頁籤 ID 與原 `tab_label` 做相容遷移；不能確定歸屬的列保留原資料並回報診斷，不靠同名頁籤猜測或刪除原列。對系統預設商品的「移動出去／移除」，寫入的只是目前使用者、目前系統頁籤的隱藏覆寫；複製到另一系統頁籤只建立該目的頁籤的成員資格。目的地已存在時保留其原 metadata，只調整第一位排序。

考慮過繼續共用空 `tab_id` 加上前端合併，但資料庫主鍵會讓跨系統頁籤的同商品互相覆蓋，刷新後無法保證兩邊都存在，因此不可採用。

### 4. 新增精確範圍、原子寫入的 mutation

新增具明確來源／目的 `tabKey`、商品代號及 `move|copy` 模式的單一 transfer API，另提供具來源 `tabKey` 的 quick-remove API；使用者身分由已驗證的 request principal 取得，不能由 payload 指定。伺服器依最新有效清單確認來源成員、兩個頁籤均啟用且不相同、目的地現況與合法排序。未驗證或過期狀態回傳明確衝突，禁止使用「只靠 symbol」的跨頁籤或全頁籤刪除。

transfer 在同一資料庫原子單位內完成目的地建立或沿用、目的地置頂、其餘位置重排，以及 `move` 的來源移除／隱藏；`copy` 不動來源。quick-remove 只處理確切來源。伺服器以當下有效成員計算新順序，不採納前端提交的整份過期排序；完成後回讀受影響頁籤成員及順序，再回傳成功。若既有 debounce 排序尚未落地，前端先等待其完成並刷新，失敗則不進行轉移。保留既有清單同步與圖表刷新機制，但不可引入新 login、下單或直接訂閱。

考慮過前端依序呼叫 `POST /api/instruments`、`POST /api/instruments/reorder` 與 `DELETE /api/instruments/:symbol`，但其中任一步失敗就可能遺失來源或留下錯誤順序，因此不可採用。

### 5. 成功後最小化更新，失敗不樂觀刪除

請求 pending 時鎖定同一卡片及涉及頁籤的重複操作。只有伺服器成功並回讀後才更新本地清單；複製保持目前頁籤及畫面不變，移動／移除只按當前清單的 canonical 順序填補受影響卡片，優先下一個、最後一個時上一個，空清單顯示空狀態，不重置其他線圖的商品或 viewport。衝突時重新讀取並告知重試；網路失敗時不宣稱成功，也不從 UI 提前刪除來源。

## Risks / Trade-offs

- [系統頁籤舊資料共用空 `tab_id`] → 新增 per-system-tab 覆寫及相容解析，保留舊列，逐項回歸管理畫面的新增、排序、刪除與還原。
- [同一商品可能是預設項、舊個人覆寫或新目的地成員] → 以穩定頁籤 identity 及唯一成員鍵判斷；目的地已存在時保留自己的 metadata、不新增重複列。
- [未落地排序與拖曳轉移競爭] → 等待現有排序寫入／讀回後再發 transfer；在 mutation 期間封鎖同一來源與目的地的重複操作。
- [線圖顯示代號與清單所屬代號分離] → 不一致時停用快捷操作，並在伺服器重新核對來源成員。
- [D1 與本機 SQLite 行為差異] → 以正式 D1 相容的原子寫入和失敗注入測試驗證；若無法保證原子性，保持功能不可用，不以多個獨立請求取代。

## Migration Plan

先新增不破壞舊表的系統頁籤覆寫儲存與讀取相容層，再使既有管理 API 與新快捷 API 共用有效清單解析；確認舊系統覆寫與共享預設的逐頁籤結果後才開啟新 UI。部署時不清空舊列、不重建清單，也不修改 RealTimeStock。回退 UI 時保留新資料表並繼續由相容讀取層呈現；若伺服器相容層無法安全回退，先停用寫入並保留資料供修復。

## Open Questions

無需阻擋 proposal 的使用者選擇。實作前須以本機及 D1 整合測試確認舊系統覆寫列的實際分布、相容遷移與原子寫入行為；遇到無法判定頁籤歸屬的舊列，保留資料並明確列出待處理，不自行猜測。

## Context

`openIntradayStockSelectionWindow` 同步以 `window.open(url, '_blank', 'noopener')` 開啟同源專用版面。HTML 標準允許 `noopener` 在成功建立新分頁後仍回傳 `null`；目前「版面」選單卻用回傳值的真假顯示「已阻擋」alert，形成每次成功開頁也可能出現的誤報。既有「選股篩選」入口已採用同樣的安全開頁方式，但不以空回傳推論阻擋。

## Goals / Non-Goals

**Goals:**

- 成功開啟盤中選股時，來源看盤頁不再出現錯誤的阻擋 alert。
- 維持 `noopener`、同步使用者操作、專用 layout URL 與來源 workspace 隔離。
- 真正阻擋開頁時保留瀏覽器原生阻擋指示及原入口可重試能力，不把未開頁說成監控已啟動。

**Non-Goals:**

- 不要求繞過瀏覽器的 popup 政策，也不改變使用者的瀏覽器權限。
- 不新增開頁成功的跨分頁握手；本變更不修改行情、監控 lease、訂閱或交易流程。
- 不改動 MultiView 與收盤後「選股篩選」入口。

## Decisions

1. 盤中選股入口保留現有 `window.open(..., 'noopener')`，但不再依回傳值顯示自製 `window.alert`。這是最小修正，也與同一選單的「選股篩選」入口一致；不改用可取得 window handle 的非 `noopener` 呼叫，以免降低隔離性。
2. 真正被瀏覽器阻擋時，由瀏覽器原生阻擋指示告知使用者；「版面 → 盤中選股」仍是可再次點擊的重試入口。不得用無法區分成功與阻擋的 `null` 顯示肯定語氣的自製通知。
3. 將原本以 mock 非空回傳代表成功、空回傳代表阻擋的 browser test 改成驗證：空回傳仍呼叫安全開頁、關閉選單且不顯示 alert／不變更來源版面。保留 URL 與 `noopener` 單元測試。

## Risks / Trade-offs

- [無法在來源頁僅靠 `window.open` 回傳值精確判定 popup 是否被阻擋] → 不假造狀態；使用瀏覽器原生阻擋指示與相同入口重試。若日後需要產品內精確狀態，須另設可驗證的開頁握手並另行評估失敗逾時語意。
- [移除 alert 後，未注意瀏覽器原生提示的使用者可能不知道如何重試] → 版面入口保持可見與可重按；驗證主流瀏覽器的原生阻擋情境，不以假警告干擾成功開頁。

## Migration Plan

只更動前端入口與測試，不需資料遷移或服務重啟。若驗證發現回歸，可回復入口的前端變更；不得以移除 `noopener` 作為回退方案。

## Open Questions

無。若未來要求產品內辨識「確實被阻擋」而非依賴瀏覽器原生提示，另立設計處理可驗證握手與逾時。
